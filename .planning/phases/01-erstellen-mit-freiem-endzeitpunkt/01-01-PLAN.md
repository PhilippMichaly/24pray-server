<objective>
Organisatoren legen Gebetswachen mit einem eigenen Enddatum samt Uhrzeit an, statt ausschließlich über feste Dauer-Presets.

**As a** Organisator:in **I want to** im bestehenden Erstellungsformular zusätzlich zu den Dauer-Presets einen eigenen Endzeitpunkt (Datum + Uhrzeit, minutengenau) eingeben **so that** die Gebetswache exakt meinen tatsächlichen Gebetszeitraum abdeckt und nur vollständige Stunden-/Tages-Slots enthält.

Purpose: Phase 1 des Meilensteins „Freie Zeiträume" — reine Frontend-Phase im Sibling-Repo `24pray-web`; die API (`POST /projects`) bleibt unverändert und validiert serverseitig weiterhin nur die Spanne (Ende nach Start, höchstens 366 Tage).
Output: Custom-End-Eingabe im Dauer-Raster, clientseitige Slot-Ausrichtungs-Validierung (neu, da die API sie nicht erzwingt), vollständige i18n-Abdeckung in de/en/es/he/ar.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser-Formular → POST /projects | Unvalidated client state (customEnd) leaves the trusted client validation path; a crafted request can bypass it entirely. |
| Fehlertexte/Beispielwerte → DOM | User-influenced strings (customEnd-derived example end) are rendered into the page. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | POST /projects payload (client-validation bypass) | medium | accept | Server-side span validation (endDate after startDate, span ≤ 366 days) remains enforced unchanged in 24pray-api/src/schemas/projects.ts:21-28. Slot alignment is client-side only this phase — a crafted client could create misaligned slots; documented scope-excluded residual risk (RESEARCH A5, REQUIREMENTS out-of-scope table). Normal flow is gated: invalid custom end never POSTs (D-14). |
